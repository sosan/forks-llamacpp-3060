I'm building a data pipeline that processes around 50 million JSON records per day. Each record is roughly 2 KB and contains nested objects, arrays of timestamps, and some free-text fields in multiple languages. The pipeline currently runs on a single PostgreSQL 16 instance with 128 GB of RAM and 8 NVMe drives in RAID 10.
The current workflow is straightforward: an ingestion service writes raw records into a staging table, a series of SQL transformations normalize the data into a star schema, and a materialized view refreshes every 15 minutes to serve a dashboard. This worked fine until the dataset grew past 30 billion rows. Now the refresh takes 22 minutes, the staging table accumulates WAL faster than the archiver can keep up, and the dashboard occasionally shows stale data.
I've been reading about three possible directions:
1. Partitioning the fact tables by month and using incremental materialized view refreshes instead of full refreshes. PostgreSQL 16 supports partitioning, but I'm not sure how it interacts with the foreign keys that reference the dimension tables. I also want to distinguish features available in core PostgreSQL from features that require extensions or a different refresh strategy.
2. Moving the transformation layer to Apache Spark or Flink and writing the results back to PostgreSQL only for serving. This would decouple ingestion from transformation, but introduces a second system to operate and monitor.
3. Replacing PostgreSQL entirely with ClickHouse or TimescaleDB, since most queries are analytical and read-heavy. The free-text fields and nested JSON would need careful handling, though, and we have a few write-heavy use cases, including real-time alerting on incoming records, that need low-latency inserts.
Here are the specific questions I need help with.
For option 1: What is the recommended way to partition a fact table that has foreign keys to slowly changing dimension tables? Do I need to change the foreign key constraints, or can I partition only the fact table and leave the dimensions as they are? If the dimension rows have validity intervals, how should the fact table retain the correct historical dimension version? Also, does core PostgreSQL provide row-level incremental maintenance for materialized views, or would I need to build an incremental summary table myself?
For option 2: If I go with Spark, should I use batch mode with scheduled runs every few minutes, or streaming mode with micro-batches? The latency requirement for the dashboard is about 5 minutes, which is relaxed enough for micro-batches. But I'm concerned about the operational complexity of running a Spark cluster alongside PostgreSQL. What monitoring and alerting would you set up to catch silent data drift between the source and the served tables?
For option 3: ClickHouse looks promising for analytical queries, but I've read that its handling of updates and deletes differs from PostgreSQL's. We need to correct historical records occasionally, maybe 0.1% of rows per day, usually within 48 hours of insertion. Is CollapsingMergeTree or ReplacingMergeTree a good fit for this, or would I end up fighting the engine? For nested JSON fields, is it better to flatten them into columns at ingestion time or retain a flexible representation for fields that are rarely queried?
Beyond these three options, I'm open to architectural suggestions I haven't considered. Would it make sense to keep PostgreSQL as the source of truth but add a separate analytical store? Would a data lakehouse approach with Iceberg tables on S3 and a query engine such as Trino be overkill for a dataset currently around 60 TB and growing by roughly 2 TB per month?
I'd also like to understand the trade-offs in team effort. We have three backend engineers and one SRE. None of us has production experience with Spark or Flink, but we're comfortable with PostgreSQL, Python, and basic Kubernetes. How much ongoing maintenance would each option realistically require after the initial setup, and what failure modes should we expect in the first few months?
Some additional context may help. The dashboard is used throughout the day by about 400 employees. Most views aggregate counts, rates, and percentiles across a few dimensions and time ranges. Typical queries cover the last seven days, while a smaller group of analysts runs historical comparisons across several years. The dashboard does not require every new record to appear immediately, but a delay longer than five minutes should trigger an alert. Historical queries can take longer, provided they do not interfere with recent-data queries.
A few more details about our query patterns. The busiest dashboard panel groups events by customer and by hour for the last 24 hours, and it must render in under three seconds. A second panel compares this week against the previous four weeks by day, which currently scans a lot of rows. Analysts occasionally export a filtered summary to a spreadsheet, and two or three times a month someone runs an ad-hoc query that touches a full year of data. These ad-hoc queries sometimes run for minutes, and when they coincide with the materialized view refresh, dashboard latency degrades noticeably. I would like advice on how to isolate or rate-limit such queries, whether through connection routing, resource queues, separate serving copies, or cancellation policies.
The ingestion rate is uneven. Most hours are predictable, but twice a day we receive bursts that can reach three times the usual volume for 20 to 30 minutes. Retries from upstream producers sometimes deliver duplicate records. Each event has a stable source identifier, but events can arrive out of order, and about 2% arrive more than an hour late. A much smaller number arrive several days late. The current staging process handles duplicates through a uniqueness check, which becomes expensive when ingestion spikes.
Corrections are another complication. An upstream system can resend an event with corrected timestamps, revised classifications, or updated free-text fields. We must preserve enough history to explain why a dashboard value changed, but the dashboard should display the latest accepted version. Deletions are uncommon, yet we need a documented procedure for removing records in response to retention or privacy requests. I would like to know how each proposed architecture handles corrections without requiring a costly rewrite of large historical partitions.
The fact table currently stores an event identifier, an ingestion timestamp, an event timestamp, several dimension keys, a numeric measurement, a status code, and a reference to the original JSON record. The dimensions include customers, devices, locations, and classifications. Customer and location attributes can change over time, so some dimensions follow a slowly changing dimension pattern. One concern is that a correction to a dimension must not silently change the interpretation of historical facts.
We retain raw events for 13 months in the primary system. Aggregated data must remain available for five years. Analysts occasionally need to revisit the raw records behind an unusual aggregate, but this is not a frequent interactive query. It may be acceptable to move older raw data to cheaper storage if retrieval remains possible within a few hours. Please consider whether this retention pattern changes the case for keeping everything in one database.
At present, backups use PostgreSQL base backups and continuous WAL archiving to object storage. Our recovery objectives are a maximum of one hour of data loss and four hours to restore service. We have not tested a full restore at the current data size recently, which is itself a risk. Any migration proposal should account for backup verification, disaster recovery, schema changes, and the ability to replay or rebuild analytical tables from a trusted source.
The operational budget is limited. We can buy additional machines if there is a clear benefit, but we would prefer not to operate a large distributed cluster merely to meet a five-minute dashboard target. Managed services are an option if their recurring costs are predictable. We also want to avoid an architecture where a single engineer becomes the only person capable of diagnosing failed ingestion jobs at night.
Security and compliance add constraints. The free-text fields occasionally contain personal data, so access to raw records must be restricted to a small group, while aggregates remain visible to everyone. We already redact some patterns at ingestion, but the rules change a few times a year and occasionally need to be applied retroactively. Any target system must support column-level or row-level access policies, encryption at rest, and an audit trail of who queried what.
